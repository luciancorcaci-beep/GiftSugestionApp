# Test Plan - Full Implementation

**Date**: 2026-09-18 (revised — see Revision Note)
**Author**: QA Agent
**Scope**: Full implementation — Epic 1 (Foundation) + Epic 2 (Recommendation Engine, now catalog-backed) + Epic 3 (Curated Gift Catalog), including the abuse-control, product-link-trust, and CSP hardening carried forward from Epic 1/2 remediation

## Revision Note

This plan supersedes the 2026-09-17 version in place. Epic 3 replaced the AI-based (Claude) recommendation engine with matching against a bundled, curated gift-idea catalog. The following scenarios from the prior version were **removed** because the behavior they tested no longer exists in the app:
- Provider-adapter-specific tests for `ClaudeRecommendationClient` (deleted in Story 3.3)
- The global concurrency-limiter test (`ConcurrencyLimiter`/`SERVICE_BUSY`, retired in Story 3.3 — no longer meaningful once matching is synchronous and in-memory)
- The provider-timeout test (`AbortController`/`PROVIDER_TIMEOUT`, retired in Story 3.3 — no external call to time out)
- The provider-rate-limit-error test (`ProviderRateLimitError`, retired during story 3.3's remediation pass — Claude-specific, no longer reachable)

New scenarios cover the catalog matching algorithm (age → relationship → interest-score → fallback → random-pick-3), the catalog data itself, and the no-external-AI-dependency proof.

## Scope

**Coverage**: The entire "What Gift Should I Choose" MVP — backend health/error/logging foundation, frontend shell and form, FE/BE walking-skeleton integration, input validation domain model, catalog-backed recommendation matching, and the gift form/results experience including security headers.

**In Scope**:
- Form input capture (age, budget, relationship, interests) and client + server validation
- `GET /api/health` and `POST /api/gift-suggestions` endpoints
- Catalog matching algorithm: age range, relationship tags, interest/keyword scoring, fallback, randomized selection
- Catalog data integrity (150 entries, converted from the source spreadsheet)
- Recommendation generation contract (exactly 3, required fields, trusted product links)
- Loading/error/empty/retry UI states
- Rate limiting and request body size cap (still-valid abuse controls; concurrency limiting and provider timeout are retired — see Revision Note)
- Security response headers, including the CSP nonce mechanism
- Shared UI primitives (`Button`, `Input`, `Select`, `Card`)
- No external AI/Claude dependency anywhere in the running app

**Out of Scope** (per `docs/requirements.md`):
- User authentication/accounts, multi-user RBAC
- Marketplace checkout/payment processing
- CRM/inventory integration, analytics dashboards
- Multi-language support
- Distributed/cross-instance rate limiting (documented as an accepted MVP limitation pending an architecture decision — see `docs/reviews/all-stories-code-review-v3.md` Comments)
- Live end-to-end proof with a real Claude API key (moot — there is no longer a Claude integration to test)

## Test Categories

### Unit Tests
- Input validation (`validateGiftInput`): required fields, type coercion, range checks, relationship enum, unknown-field rejection
- Catalog matching (`CatalogRecommendationProvider`): age eligibility, relationship eligibility, interest scoring, fallback, randomized selection, rationale/relationshipFit synthesis
- Catalog loading (`giftCatalogLoader`): entry count, uniqueness, field shape
- Domain services: `RecommendationService` exactly-three enforcement, error mapping, product-URL sanitization
- Shared utilities: `FixedWindowRateLimiter`, `readBoundedJson`, `isTrustedProductUrl`
- Error taxonomy (`AppError` hierarchy) → HTTP status/code mapping
- Logging: structured output, secret/PII redaction
- Shared UI primitives: `Button`, `Input`, `Select`, `Card` markup/accessibility

### Integration Tests
- `POST /api/gift-suggestions` end-to-end through the handler → service → catalog-provider boundary (both mocked-provider unit tests and the real default `CatalogRecommendationProvider`)
- `GET /api/health` route
- `GiftForm` ↔ `GiftResults` interaction through the real component tree (submit → loading → render / error / retry)
- `middleware.ts` header/CSP-nonce behavior at the request/response level

### E2E / Manual Tests
- Real production server (`next build && next start`) browser-level verification: nonce match on served HTML, hydration/interactivity actually works under the enforced CSP
- Real production server with **no `.env` file present at all**: confirms the app returns real catalog-backed recommendations with zero AI-provider dependency
- Manual full user journey: fill form → submit → see three cards → click a product link (or confirm it's omitted if untrusted)

## Test Data Requirements

- **Valid set**: `{ recipientAge: 28, budget: 75, relationship: "Friend", interests: "coffee, hiking, books" }`
- **Catalog-eligible set** (known to match a real category): `{ recipientAge: 30, budget: 50, relationship: "Friend", interests: "music" }`
- **Boundary set**: `recipientAge: 0`, `budget: 0.01`, `interests` at exactly 500 chars; recipient age exactly equal to a known catalog entry's min/max age
- **Invalid/malicious set**: missing fields, `relationship: "Coworker"`, negative age/budget, non-numeric strings, payload with an extra unknown key, oversized JSON body (>16KB), HTTP/untrusted-domain `productUrl` values, spoofed `X-Forwarded-For` headers
- **No-match set**: `interests: "xyzzyx123nomatch"` (matches nothing, to exercise the fallback path)
- **Provider mocks** (for `RecommendationService`-level unit tests): success (3 well-formed items), malformed (wrong count / missing fields), generic failure

## Environment Requirements

- Local dev: Node (project's configured version), `npm test` / `npm run test:coverage` (vitest, mixed `node`/`jsdom` environments via `environmentMatchGlobs`)
- Local build/E2E: `npm run build && npm run start` on a scratch port, verified via `curl`. For TC-042, run with **no `.env` file present at all** (temporarily move it aside, restore afterward) — this is the definitive proof of no AI dependency.
- No database or external state to reset between runs (no persistence layer in this MVP)
